# HARMONY Coding Standards & Review Guidelines

This document defines repository standards and architectural conventions evaluated during code review.
Automated checks and mechanical invariants are enforced by `tests/check_invariants.sh`.

---

## 1. Architectural Invariants & Core Freeze

- **Frozen Runtime Core (`dcl/`)**: The `dcl/` directory is 100% frozen. Under no circumstances should runtime engine headers (`dcl/*.hpp`) or source files (`dcl/*.cpp`) be modified. All variance investigation and performance evaluation harnesses must remain external.
- **Minimal Driver Adjustments**: Benchmark drivers (`benchmarks/*.cpp`) and preflight tests (`tests/*.cpp`) may only receive minimal, surgical modifications when explicitly authorized by an issue (e.g., isolating loop duration before validation, enforcing per-rank GPU counts).
- **Frontend Build Only**: Never trigger compilation (`mpic++`, `cluster_build.sh`) inside compute node jobs or batch execution scripts. Compute node scripts must verify prebuilt binaries in `build/cluster` and exit with an error if missing.

---

## 2. Artifact Identification & Consistency

All scripts, post-processing tools, and documentation must strictly use standard artifact filenames:

- **`run_manifest.json`**: Single source of truth for job execution parameters, seed schedules, and per-sample status/exit codes.
- **`hardware_telemetry.log`**: Raw multi-node `nvidia-smi` telemetry snapshots (tagged with `host, rank`).
- **`hardware_telemetry.json`**: Structured telemetry records parsed from all participating GPU nodes.
- **`super_matrix_summary.csv`**: Aggregated sample wall times, loop durations, balance metrics, and boundary shifts.
- **`super_matrix_paired.csv`**: Paired comparison speedups (ERAD vs. HWTOPOLB) and repetition ratios.
- **`SUPER_JOB_REPORT.md`**: Human-readable Markdown diagnostic report generated by `analyze_super_matrix.py`.

*Rule*: Do not introduce or document divergent artifact names (e.g. `super_matrix_paired_ratios.csv` or ad-hoc filenames).

---

## 3. ADR & Spec Reconciliation

- **Amendment on Boundary Changes**: If an approved ticket or review fix modifies a boundary previously specified as out-of-scope or frozen by an Architectural Decision Record (ADR) (e.g., touching benchmark drivers while runtime is frozen), the change must include a dated `## Amendment (YYYY-MM-DD)` section in the relevant ADR (e.g., `docs/adr/0001-non-invasive-pbs-super-job.md`).
- **Single Source of Truth**: The ADR amendment, `README.md`, and issue tracker must remain synchronized in the same commit or PR.

---

## 4. Empirical & Bounded Assertions

- **Bounded Diagnostic Verdicts**: Diagnostic conclusions must report observed empirical metrics (median, min, max, repetition counts) rather than unverified causal claims. Do not state that an observed slowdown is caused by compilation caches, CPU-GPU contention, or thermal drift unless corroborated by recorded telemetry.
- **Named Heuristic Thresholds**: Any numeric cutoff used to classify diagnostic outcomes (e.g., performance parity vs. anomaly) must be declared as an explicit, named module constant labeled `HEURISTIC_*` and documented as non-causal guidance.

---

## 5. Domain Vocabulary Compliance

Always use terms as defined in [`GLOSSARY.md`](GLOSSARY.md):

- **Super Job driver**: Use "Super Job driver" or "runner" for the batch execution script. *Avoid*: "orchestrator", "orchestration", "multi-stage pipeline".
- **Historical Evidence**: Use "historical log", "historical run", or "preliminary evidence". *Avoid*: "legacy log", "old run".
- **Standard Stages**: Use "preflight", "untimed warm-up", "rotated matrix", and "A/B/A test".
